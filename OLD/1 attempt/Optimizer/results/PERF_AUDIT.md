# Аудит производительности Optimizer (перед этапом 3)

Цель: ускорить расчёт без изменения физической модели, формул, ограничений
и результатов. Ни одна проверка и ни одна точка сетки не сокращены.

## 1. Профилирование

`cProfile` на трёх кандидатах (CPU-время, без учёта конкуренции процессов):

| функция | cumtime, с | доля |
|---|---|---|
| `eval_candidate` | 3.32 | 100 % |
| `распределить_π_const_hub` | 3.31 | 99.8 % |
| `турбина_const_hub` | 3.30 | 99.5 % |
| `ступень_const_hub` | 3.23 | 97 % |
| `ступень` (ядро) | 2.70 | 81 % |
| `cp_k_ступени` | 1.49 | **45 %** |
| `газ` | 1.12 | 34 % |
| `calc_cp_kerosene` | 0.51 | 15 % |
| `np.interp` | 0.26 | 8 % |

Вызовов на одну оценку кандидата:

```
ступень                 5 940
ступень_const_hub         675
турбина_const_hub         225
распределить_π             15
газ                    49 253
calc_cp_kerosene      147 758
np.interp               5 704
```

Вывод: время уходит не на проверки ограничений, а на внутренние итерации
`ступень_const_hub` (фиксированная точка по ρ, D) и `cp_k_ступени`.

Ключевое наблюдение: в цикле фиксированной точки `ступень_const_hub`
аргументы `T0, p0, H0` **не меняются**, а `cp_k_ступени(T0, H0)` вызывается
заново 8–9 раз. Это чистые функции — их можно кэшировать без изменения
результата.

## 2. Что сделано

| изменение | эффект | риск |
|---|---|---|
| `lru_cache` на `cp_k_ступени(T0,H0)` | 96.6 % попаданий | нет: чистые функции, ключ — точные float |
| `lru_cache` на `газ(T)` | 8–18 % попаданий | нет |
| `lru_cache` на `H0_по_p(T0,p0,p2)` | ~18 % попаданий | нет |
| `np.interp` → линейный интерполянт `_линейно` | −8 % времени | проверено бит-в-бит на 200 000 точках |
| убран лишний пересчёт в цикле подбора G | −1 вызов `распределить_π` из ~6 | нет: при сходимости результат тот же |
| `--workers` через `ProcessPoolExecutor` | 2.8× на 8 процессах | нет: детерминированное разбиение |

Кэш ограничен (8192 записи на процесс), накапливается в пределах одного
`ns`; ключи — точные значения float, попадания возвращают тот же объект.
Порядок арифметических операций в модели не менялся.

Нумба не применялась: горячий путь — итерации с исключениями и словарями,
JIT потребовал бы переписать ядро, а это риск изменить результаты.
Адаптивная сетка не применялась: по условию сетка 31³ остаётся полной.

## 3. Проверка идентичности

20 случайных точек в границах оптимизатора, `fast=False` против `fast=True`:

```
отличий: 0 / 20;  max |Δ| = 0.0
lc1, a2, rho, rho_root, sigma, qn, N, eta_t, hard, score1, score2
```

Проверка воспроизводимости при разном числе процессов: сетка 5³ (125 точек),
CSV побайтово совпали при 1, 2 и 4 процессах (`md5` одинаковый).

## 4. Масштабирование по процессам

Сетка 8³ = 512 точек, один и тот же расчёт:

| процессов | время, с | ускорение |
|---|---|---|
| 1 | 35.3 | 1.00× |
| 4 | 15.6 | 2.26× |
| 6 | 15.9 | 2.22× |
| 8 | **12.8** | **2.76×** |
| 12 | 13.9 | 2.54× |

Контейнер видит 16 CPU, но хост — Ryzen 7 PRO 5850U: 8 ядер / 16 потоков,
частота под нагрузкой ~60 %. Дальше 8 процессов упирается в SMT и память,
поэтому выбрано `--workers 8`.

Стоимость одной оценки: 0.069 с на одном ядре (простой хост) против
0.09–0.12 с до оптимизации; при одинаковой нагрузке CPU-время упало
с 0.340 до 0.188 с (1.8×).

## 5. Что осталось

- Кэш `cp_k_ступени` не переживает пересоздание `ns`; для сетки это неважно.
- Дальнейшее ускорение — только переписывание ядра (`ступень`) или
  сокращение итераций фиксированной точки; и то и другое меняет результаты,
  поэтому не делалось.
- Полная сетка 31³ × 2 = 59 582 оценки прошла с `--workers 8`:
  A — 7.5 мин, B — 9.2 мин, всего ~17 мин (до оптимизации прогноз был
  ~21 мин на конфигурацию, ~42 мин на обе). Ускорение сквозного прогона
  ≈2.4× при том же числе точек.

## 6. Файлы

- `optimize_extended.py` — `build_ns(..., fast=True)` и `_линейно`,
  кэш чистых функций.
- `scan3d.py` — `--workers` (ProcessPoolExecutor), детерминированное
  разбиение по индексу `n`, сортировка результата, один писатель CSV.
- `run_scan3d.sh` — прогон A и B с 8 процессами, затем слияние.

## 7. Проверки после изменений

- `python -m py_compile` для затронутых файлов — ок.
- Идентичность 20 точек — ок (0 отличий).
- Воспроизводимость 1/2/4 процесса — ок (побайтово).
- Сетка и ограничения не менялись; число оценок не сокращалось.

## 5.4. Следующая методическая проверка

Перед воспроизведением reference points и тем более перед сравнением архитектур:

1. создать контролируемый реестр уравнений (сейчас `docs/engineering/EQUATIONS.md`
   отсутствует; создавать его содержание по памяти нельзя);
2. разрешить `c_p`, `alpha`, отборы/`C_e` и структуру турбины;
3. проверить по обеим версиям кейсов выбранные pressure ratios, межвальные балансы,
   остаточную кинетическую энергию и stage equations относительно печатных страниц,
   с фиксацией переменных/единиц/знаков;
4. только после этого решать, воспроизводить ли кейсы Сергея/Антона как внешние
   сравнения.

Не запускать optimizer, DE или sweep в рамках этой методической проверки.

## 6. Плоскость мощности 110 кВт: подтверждённый контракт

Пользователь явно подтвердил (2026-11-10): **110 кВт — механическая мощность на
входе редуктора, до потерь редуктора**. Это больше не открытый вопрос о
gearbox input vs propeller shaft. Редуктор — отдельный downstream-элемент.

Активные формулы (pre-reducer target plane):

```text
N_ud              = L_t * (g_t + g_return) * eta_mech_turbine - L_k
G                 = N / N_ud
N_reducer_out_ud  = N_ud * eta_reducer          # downstream gearbox output
R_ud              = g_sum * (c_c - v)
N_e_ud            = N_reducer_out_ud + (R_ud / beta_prop        if v == 0
                                        else R_ud * v / eta_propeller)
C_e               = g_m * (1 - g_leak - g_cooling) * 3600 / (N_ud / 1e3)
eta_e             = 3600 / (C_e * q_lhv_kj)
```

Где это в коде:

- `turbine_engine/cycle.py` `calculate_cycle_point`: `N_ud` (строка 511),
  `N_reducer_out_ud` (512), `N_e_ud` (514–518), `C_e` (527), `eta_e` (528).
- `turbine_engine/baseline.py` `N_на_валу` (446–478): `N_в = L_тΣ G_c1 η_м -
  G_в L_к`, без `η_р`.
- `turbine_engine/performance.py` `calculate_turbine_performance`: `N_shaft`
  (170) и явный downstream `N_shaft_reducer_out` (171).
- `Optimizer/optimizer_core.cycle_point`: явные `N_reducer_out_ud` и
  `d["N_ред_уд"]` (190, 199).
- `Optimizer/optimize_extended.eval_candidate`: масштабирование расхода по
  pre-reducer `N` (208–220), без `η_р`.

Смысловые ограничения:

- `C_e`/`eta_e` теперь отнесены к **входной** (pre-reducer) плоскости, как
  требует выбранная цель. Это не топливная экономичность на винте; при
  необходимости downstream-метрика получается умножением/делением на `η_р`
  и должна быть подписана явно.
- `N_e_ud` — эквивалентная мощность «вал на выходе редуктора + тяга сопла».
  Она намеренно не смешивает pre-reducer `N_ud` с тягой; поэтому её численное
  значение совпадает с прежним legacy `N_e_уд`.
- Legacy-числа прежней post-reducer трактовки сохранены только как
  маркированный differential в `scripts/test_cycle_point_regression.py`
  (`LEGACY_ANCHORS` / `test_legacy_post_reducer_anchor_is_a_labelled_differential`).
  Активные anchor-значения пересчитаны по точным соотношениям, а не заменены
  без основания.
- Это изменение формулы по решению пользователя, а не физическая валидация.
  Чтобы не оставлять устаревшие downstream-результаты (включая ступени и
  геометрию), у **всех** code-ячеек обоих активных source-ноутбуков
  (`Turbinis-Cycle`, `Turbinis-Calc`) очищены cached outputs и
  `execution_count`. Source-код не переписывался; sweep/повторное исполнение
  ноутбуков не выполнялось.

| `SINGLE_SHAFT_DUAL_CC` (A) | два CC последовательно → один combustor → turbine | два CC и turbine на одном валу | общий shaft → reduction gearbox → propeller |
| `SINGLE_SHAFT_SINGLE_CC` (B) | один CC → combustor → turbine | CC и turbine на одном валу | turbine shaft → reduction gearbox → propeller |
| `FREE_POWER_TURBINE` (C) | CC + gas-generator turbine на одном валу; отдельная free-power turbine | gas-generator shaft и free-power-turbine shaft раздельны | free-power-turbine shaft → reduction gearbox → propeller; gas-generator shaft output не приводит |

Буквенные метки соответствуют `Super-Promt-Autonomous.md` §6:
**A — одновальная, два ЦБК; B — одновальная, один ЦБК; C — двухвальная
со свободной силовой турбиной.** Это метки выбора, а не имена enum:
стабильные значения `SINGLE_SHAFT_DUAL_CC`, `SINGLE_SHAFT_SINGLE_CC` и
`FREE_POWER_TURBINE` не переименовываются.

Это ровно то, что кодирует `turbine_engine/architecture.py` (`ARCHITECTURES`,
`ShaftGroup`, `ArchitectureDescriptor`). Контракт остаётся концептуальным:
числа compressor/turbine units — это assembly counts, **не** aerodynamic stage
counts. Не заданы и не должны выдумываться: число ступеней, shaft rpm, gear
ratio, gearbox efficiency (кроме существующего cycle `eta_reducer`), propeller
load, pressure split, flow splits, bleed topology. Gearbox/propeller — только
downstream topology statement; отдельного компонента/КПД/нагрузки в checkout
нет.

### 8.1. Источник границы последней ступени (закрыто только для этого guard)

Прямая сверка PDF турбинного учебника (часть 1), печатная пагинация:

- **Печ. с. 92 (PDF с. 93), пп. 138–140.** Для последней ступени задано
  `p2z = p_t` и
  `H0z = cp*T0z*[1 - (p2z/p0z*)^((k-1)/k)]`. При положительных `cp`, `T0z`
  и `k > 1` положительный `H0z` существует только при `p0z* > p_t`.
  Процентного запаса в этом уравнении нет. Поэтому `p0 <= p_t` — граница
  отсутствия положительного перепада, а не «z слишком велико».
- **Печ. с. 93 (PDF с. 94), пп. 142–145.** Там описано **другое** замыкание —
  по заданной работе: `L_tz = (L_total - sum(L_ti*g_i))/g_z`, назначенный
  `eta_tz`, `H0z = L_tz/eta_tz`, затем ищется выходное давление под требуемую
  работу. Это не то же самое, что prescribed `p2z = p_t`, и их нельзя
  смешивать в одном расчёте без явного выбора постановки.
- **Печ. с. 84, §9.** Зафиксированы два варианта граничных условий:
  одновальная турбина с заданным выходным давлением и турбина, связанная с
  компрессором по заданной работе.
- **Печ. с. 5–7, §1.1.** В многовальной схеме турбина компрессора
  определяется мощностью компрессора; её выходное давление — результат
  баланса, а не произвольно назначенная величина.
- **Печ. с. 18, ур. 8.** `L_t = cp*(T_g* - T_t*)` без теплообмена —
  контрольная балансовая форма, не заменяющая ступенчатую методику.

Важно: в `Turbinis-Calc/book-scan.md` маркеры страниц сдвинуты. Строка 1933
помечает с. 91, хотя формула 140 находится на печ. с. 92; строка 1962
указывает с. 92, хотя фактические пп. 142–145 — на печ. с. 93. Здесь и в коде
используются фактические печатные страницы PDF, а не ошибочные маркеры
Markdown. История guard: `p0 <= 1.02*p_t` присутствовал в исходной notebook
cell 16 и был перенесён в extracted module как «source-preserving»; при
прямой сверке PDF обоснования этого запаса не найдено, поэтому он удалён и в
module, и в notebook. Эта сверка подтверждает только границу `p0 > p_t` и
наличие альтернативного замыкания; она **не** является полной валидацией всех
ступенчатых формул, потерь, охлаждения или геометрии.

### 9.1. M2-замыкания архитектур (reference-реализация)

Основание: печ. с. 84 §9, печ. с. 92–93 пп. 138–145, печ. с. 5–7 §1.1.
Ниже сохранён проектный список требований; он не является физической
валидацией.

Статус (2026-11-11): standalone-баланс мощностей для трёх выбранных
архитектур реализован в `turbine_engine/shaft.py`. Opt-in исполняемые 0D
reference-циклы реализованы в `turbine_engine/architecture_cycle.py` для всех
трёх топологий с явным вариантом `uncooled_no_bleed_0d_ideal_mixing`:
закрытие A/B MAIN-вала, отдельные GG/FPT-замыкания C, передача фактического
состояния GG → FPT, prescribed **total** outlet pressure и расчёт `G` под
110 кВт pre-reducer. Fuel/air берётся из `calc_g_m` (или внешнего состояния);
`alpha` basis, gas constants и ограничения `MISSING_COMPRESSOR_PHYSICS` /
`NOT_PHYSICALLY_VALIDATED` записываются в результат. Число ступеней, rpm,
gear ratio, propeller load, cooling/map/composition по-прежнему не выдумываются.
Legacy-цикл не переписан; новые циклы не являются numerical rebaseline.

1. **GG shaft (только C).** Закрывать по мощности компрессора, а не по
   произвольному выходному давлению: `eta_mech_GG * G_GG * L_GG = N_compressor`.
   Здесь `N_compressor = G_air * L_compressor`, поэтому нельзя приравнивать
   удельные работы на разных массовых базах. Механические потери уже включены
   в `eta_mech_GG`; не добавлять их повторно. Из требуемой `L_GG` и модели
   расширения получить `p_out_GG`/`T_out_GG`, явно различая полный и статический
   КПД. У A/B нет отдельного GG-вала: их общий вал также питает полезную нагрузку.
2. **Передача состояния.** Передавать фактический `StationState` на выходе GG
   turbine (`T_total`, `p_total`, `mass_flow`, `cp`, `k`) в free-power turbine.
   Не подставлять повторно `T_g* = 1250 K`.
3. **Free-power turbine (C).** Закрывать по требуемой работе/110 кВт:
   `L_FPT_required = (N_gearbox_input + shaft_losses)/G_FPT`, затем при
   prescribed outlet pressure получить `H0`, `pi`, ступени; либо prescribed
   `p_out` и решать `G`. Stage/geometry checks выполняются после баланса.
4. **Total vs static.** Явно указывать, заданы ли `T*`/`p*` или статические
   величины; остаточную кинетическую энергию (`c^2/2`) учитывать отдельно.
   Не смешивать статическое `p_out` с тотальным `p0*`.
5. **Single-shaft A/B.** A: два compressor unit последовательно с явным
   `pi_1/pi_2` split; B: один CC. В каждой схеме один combustor и turbine assembly
   на общем валу. Баланс: `eta_mech * G_turbine * L_turbine - sum(N_compressor_i)
   = N_gearbox_input = 110000 W`. При заданном выходном давлении и рассчитанных
   удельных работах решать расход, как в текущем одновальном anchor; не применять
   compressor-only баланс C к A/B. C имеет отдельные GG и free-power shafts.
6. **Не выдумывать.** Число ступеней, rpm, gear ratio, propeller load,
   cooling flows/composition, `cp`/`alpha` closure и compressor map остаются
   явными входами или `MISSING_*`. 0D compressor component можно использовать
   без заявления map/stage validation. Проверка compressor stage inventory и
   `cp`/`alpha` consistency — предусловие содержательного сравнения A/B/C, а
   не повод придумать числа.
